# 目的
AIサービスなどの公式リリースノートを、設定ファイルに登録したサービスについて、まとめて把握できるようにする。
サービスの追加・削除は、設定ファイルを書き換えるだけで行う（このファイルは変えない）。

# 設定ファイル
config/release-notes.json（Git管理対象）。形式:
- source_list_status: 情報源リストの状態（暫定 / 確定）
- services: サービスの配列。各サービスは次の項目を持つ。
  - name: サービス名
  - enabled: true のときだけ収集する
  - sources: 情報源の配列（label と url）

設定の読み方:
- ファイルがない、JSON として読めない、有効なサービスが0件のときは、収集せずにその旨を伝える。
- 情報源のURLは、設定にあるものだけを使う。推測で追加しない。

# 引数と既定値
- 期間: 指定がなければ「前回の成果物以降」。outputs/research/*_release-notes/ のうち、最新のフォルダの日付から今日まで。前回の成果物がなければ「直近2週間」。
- サービス: 指定がなければ、設定で enabled が true のすべて。指定されたサービス名が設定にない場合は、その旨を伝える。
- 項目数の上限: 1サービスあたり10件（仮）。引数で指定があれば従う。超える場合は、新しい順に残し、省いた分は件数だけ報告する。

# 使うエージェント
新しいエージェントは作らない。既存の次の2つを使う。
- research-collector: 情報源から収集する
- research-checker: 日付・出典・内容を裏取りする

# 実行手順

## STEP 1：条件を確定する
設定ファイルを読み、期間、対象サービス、項目数の上限を確定して、一行で復唱する。

## STEP 2：過去の成果物を確認する
outputs/research/*_release-notes/topic_summary.md を読み、すでに載せた項目を把握する。
- 同じ項目は載せない。
- 続報（同じ機能の追加の更新）は「続報」として、新しい情報だけを載せる。

## STEP 3：収集する（research-collector）
対象サービスの情報源を取得するよう依頼する。
- 目的、期間、対象サービス、情報源のURL、STEP 2 の既出項目を伝える。
- 1つの情報源につき、取得は原則1回にする。連続・並列の取得を避ける。
- 取得ツールで失敗した場合は、Bash の curl で1回だけ再試行してよい。403 などで拒否されたら、回避せず「取得できなかった」と報告させる。
- 取得できなかった情報源は「更新なし」と扱わない。
- ページが長い場合は、期間内の新しい部分だけを使う。
- 各項目に、サービス名、日付、内容（原文の意味を変えない要約）、出典URLを付けさせる。
- 日付は、ページの表記（月日、地域・言語の違い）を確認し、yyyy-mm-dd に直させる。判断が分かれる場合は、その旨を書かせる。
- 情報源ごとの取得結果（取得できた / できなかった / 一部のみ）を報告させる。

## STEP 4：裏取りする（research-checker）
収集結果を渡し、日付・出典・内容を確認させる。
- 期間内か、日付がページの記載と合っているか、要約が原文の意味を変えていないかを確認させる。
- 「確認済み」と「未確認」に分けさせる。期間外の項目、出典が確認できない項目は除外または未確認とする。
- 公式のリリースノートが一次情報なので、一次情報との照合は、ページの内容との一致の確認でよい。

## STEP 5：まとめる
- サービスごとにまとめる。各サービスの中は、新しい順に並べる。
- 事実（リリースノートの記載）と、推測・意見を区別する。推測や意見は、書く場合に明記する。
- 各項目に日付と出典URLを付ける。
- 取得できなかった情報源があるサービスには、その旨を書く。

## STEP 6：保存する
outputs/research/yyyymmdd_release-notes/topic_summary.md に保存する。
- 同名のフォルダ・ファイルがある場合は上書きせず、追記するか別名にするかをユーザーに確認する。
- 結論の直前に「## 見出し一覧」を置く（CLAUDE.md の調査系のルールに従う）。各項目を通し番号付きの1行で書く。
- 期間、対象サービス、情報源リストの状態（暫定/確定）を冒頭に書く。
- 次の項目を載せる: 結論、使用したエージェント、根拠、参考サイト。

## STEP 7：報告する
保存先と、各サービスの主な更新を、3行以内で伝える。取得できなかった情報源があれば、その旨を添える。

# 成果物の形式

```markdown
# リリースノートまとめ yyyy-mm-dd

- 期間: 
- 対象サービス: 
- 情報源リスト: 暫定 / 確定
- 既出との関係: 

## 見出し一覧
1. Claude: 項目名
2. ChatGPT: 項目名

## 結論
各サービスの主な更新を、数行で。

## Claude
### 1. 項目名
- 日付: yyyy-mm-dd
- 内容: 
- 確認: 確認済み / 一部確認 / 未確認（一部確認・未確認は、確認できていない点を続けて書く）
- 出典: URL

## ChatGPT

## Gemini

## 情報源の取得状況
サービスごとに、取得できた / できなかった / 一部のみ。

## 使用したエージェント
## 根拠
## 参考サイト
```

# 注意
- URLを推測で追加しない。設定にない情報源を使うときは、実在とアクセスを確認し、ユーザーに伝える。
- 確認していない情報を「確認済み」にしない。
- 定期実行の設定はしない。呼んだときだけ実行する。
- 相手サーバーに負荷をかけない。1情報源につき取得は原則1回にし、同じサイトへの連続・並列の取得を避ける。
- 公式サイトの利用規約には、自動での取得を禁じる記載があるものがある（調査時点で Claude と OpenAI に記載あり。公開ページの閲覧に適用されるかは未確認）。このため、呼んだときだけ、必要最小限の回数で取得する。情報源を追加・確定するときは、実在とアクセスに加えて、robots.txt と利用規約を確認する。
- Gemini のページは、地域・言語で掲載内容と最新の日付が異なることがある。設定の「US・英語版」を使い、成果物にその旨を書く。
- 情報源リストが「暫定」のうちは、内容の網羅性を確定扱いにしない。
